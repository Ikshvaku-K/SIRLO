# SIRLO Visualisation Explained
### A Complete Guide to Every Output Image — From Raw Data to Fleet Intelligence

> **What is SIRLO?**
> SIRLO is a **Multi-Agent Reinforcement Learning (MARL) simulation framework** for autonomous satellite constellations. It simulates a fleet of **6 LEO satellites** operating over wildfire-prone Amazon biomes, each making independent real-time decisions — whether to image the ground, steer to a new target, downlink stored data, or idle to conserve battery. All output images below are generated by running:
> ```bash
> python src/data/run_and_visualise.py
> ```
> The script runs **3 episodes** (one per geographic region), each covering **48 time-steps × 30 min = 24 hours** of simulated mission time.

---

## How the Simulation Works — The Full Pipeline

Before diving into the images, here is the end-to-end data flow that produces them:

```
┌───────────────────────────────────────────────────────────┐
│  1. World-State Generation (per time-step)                │
│     Synthetic 8-channel 64×64 tensor                      │
│     (Cloud, Fire, NDVI, LST, Soil, Rain, Masks)           │
└───────────────────┬───────────────────────────────────────┘
                    │
                    ▼
┌───────────────────────────────────────────────────────────┐
│  2. Orbital Propagation                                   │
│     6 satellites orbit at ~90–105 min periods             │
│     Each has a (lat, lon) position computed per step      │
└───────────────────┬───────────────────────────────────────┘
                    │
                    ▼
┌───────────────────────────────────────────────────────────┐
│  3. Satellite State Computation                           │
│     Battery SoC, Storage Fill, Cloud fraction under sat,  │
│     Ground-station contact flag, Time-to-contact          │
└───────────────────┬───────────────────────────────────────┘
                    │
                    ▼
┌───────────────────────────────────────────────────────────┐
│  4. Epsilon-Greedy Policy → Action + Reward               │
│     IDLE / IMAGE / STEER↑ / STEER↓ / DOWNLINK            │
│     Priorities: low battery → IDLE | fire visible → IMAGE │
│     gs_flag=1 + full storage → DOWNLINK                   │
└───────────────────┬───────────────────────────────────────┘
                    │
                    ▼
┌───────────────────────────────────────────────────────────┐
│  5. History Accumulation (48 steps × 3 episodes)          │
│     → 13 output files: PNGs + GIF + JSON                  │
└───────────────────────────────────────────────────────────┘
```

## 📸 Image 1 — `ep{N}_world_state.png` — World-State Tensor Dashboard

> **3 files** (one per episode/region): `ep1_world_state.png`, `ep2_world_state.png`, `ep3_world_state.png`

This is the **most information-dense** visualisation. It shows the complete environmental context the satellites are observing at **Step 24 (the mid-point of the episode — T+12 h)**.

### What is the World-State Tensor?

The environment is represented as a **[8 × 64 × 64] multi-channel tensor** — think of it as 8 stacked satellite images of a 64×64 km patch. Each pixel has a normalised value in `[0, 1]`. The dashboard renders all 8 channels side-by-side, plus summary panels.

### The 10 Panels Explained

#### Panels 1–8: The 8 Sensor Channels

| # | Panel Label | What it measures | Colour logic | Real-world sensor analogue |
|---|-------------|-----------------|--------------|---------------------------|
| 1 | **GOES-16 Cloud BT** | Cloud brightness temperature (cloud cover proxy) | Blue = cold/thick cloud tops. Red = clear, warm sky below | GOES-16 geostationary IR sensor |
| 2 | **FIRMS Fire BT** | Fire hotspot intensity (Gaussian blobs around fire cluster locations) | Bright white/yellow = intense fire. Black = no fire | NASA FIRMS VIIRS/MODIS active fire product |
| 3 | **MODIS NDVI** | Normalized Difference Vegetation Index — vegetation health | Dark green = dense healthy canopy. Yellow/pale = stressed or burned | MODIS MOD13 vegetation index |
| 4 | **MODIS LST** | Land Surface Temperature | Bright/yellow = very hot (bare soil, fire scar). Dark = cool | MODIS MOD11 LST product |
| 5 | **SMAP Soil Moisture** | Volumetric soil water content | Dark blue = water-saturated soil. White = dry | NASA SMAP L-band radiometer |
| 6 | **GPM Precipitation** | Instantaneous rain rate | Deep purple/blue = heavy rainfall. White = dry | NASA GPM IMERG |
| 7 | **Cloud Mask (binary)** | Hard cloud threshold: pixel > 0.55 cloud BT = cloudy | White = cloud-blocked pixel. Black = clear | Derived from Ch.1 |
| 8 | **Fire Mask (binary)** | Hard fire threshold: pixel > 0.45 fire BT = confirmed fire | Red = active fire pixel. Black = no fire | Derived from Ch.2 |

> **Key physical correlations built into the synthetic data:**
> - Fire ↑ → LST ↑, NDVI ↓, Soil Moisture ↓ (fires dry and heat the land)
> - Cloud ↑ → Precipitation ↑, LST ↓ (clouds shade the surface and bring rain)

The **white/coloured dots** overlaid on every panel are the **6 satellites' current positions** in normalised lat/lon space. Each satellite uses a unique colour (C0–C5).

#### Panel 9: Composite False-Colour RGB

This is a single RGB composite image where:
- **Red channel = Fire BT** — fire zones appear red
- **Green channel = NDVI × 0.8** — healthy vegetation appears green
- **Blue channel = Cloud BT × 0.6** — cloud cover appears blue

The composite lets you immediately spot the spatial relationship between fires, healthy jungle, and cloud cover in a single glance. Satellite positions here are shown as **labelled circles (S1–S6)**.

#### Panel 10: Channel Statistics Bar Chart

A grouped bar chart that summarises the **entire 64×64 grid** for each of the 8 channels:
- 🟢 **Mean** — average value across all pixels (how widespread the phenomenon is)
- 🟠 **Max** — peak value (how intense the hotspot/cloud/fire is)
- 🔵 **>0.5 Cover** — fraction of pixels above 0.5 (spatial extent of detectable signal)

> This gives the RL agent's training algorithm a compact statistical summary of the world state at each step.

## 📈 Image 2 — `ep{N}_timeline.png` — Constellation Episode Timeline

> **3 files**: `ep1_timeline.png`, `ep2_timeline.png`, `ep3_timeline.png`

This is a **4-panel time-series** showing the internal state and behaviour of all 6 satellites over the **full 24-hour episode** (48 steps × 30 min).

### Panel 1 — Battery State-of-Charge (SoC)

The battery levels of all 6 satellites plotted against mission time in hours. Each satellite starts with a random SoC in the range `[0.4, 0.95]`.

**Battery dynamics:**
- IDLE costs **0.002 SoC/step** (passive power draw)
- STEER↑/↓ costs **0.005 SoC/step**
- IMAGE costs **0.015 SoC/step** (sensor + compute)
- DOWNLINK costs **0.020 SoC/step** (RF transmitter)
- Solar recharging adds `+0.005–0.012 SoC/step` at every step

The **red dashed line at 0.15** is the **low-battery threshold** — if a satellite drops below this, the policy forces it to IDLE so it can recharge rather than risk failure. The red shaded region below 0.15 highlights this danger zone visually.

> A satellite that never dips into the red zone is behaving efficiently. One that repeatedly brushes the threshold may be over-imaging.

### Panel 2 — On-Board Data Storage Fill

Shows how much of each satellite's onboard data buffer is used (0 = empty, 1 = full).

**Storage dynamics:**
- IMAGE action adds `+0.02–0.07` fill per imaging event (capturing a scene fills the buffer)
- DOWNLINK (while in ground station contact window) drains `−0.3–0.6` in a single step (bulk data transfer)

The **orange dashed line at 0.90** is the **overflow threshold** — if a satellite exceeds this without downlinking, it risks losing data or receiving a penalty (`−3` reward for >0.98 fill). The shaded orange band above 0.90 visualises the overflow danger zone.

> You can clearly see "staircase" patterns: storage climbs during IMAGE bursts and drops sharply during DOWNLINK events.

### Panel 3 — Action Heatmap

A **satellite × time grid** where each cell's colour represents the action taken by that satellite at that time:

| Colour | Action | When triggered |
|--------|--------|----------------|
| ⬛ Dark grey | **IDLE** | Low battery, heavily clouded pixel, or default filler |
| 🟢 Green | **IMAGE** | Fire detected at nadir, clear sky, battery > 0.15 |
| 🔵 Blue | **STEER↑ / STEER↓** | Repositioning to improve coverage angle |
| 🟠 Orange | **DOWNLINK** | Ground station contact window open + storage > 0.5 |

> Reading this heatmap tells you whether the constellation has a healthy **action diversity** (lots of imaging and downlinking relative to idle), or if the policy is too passive (dominated by grey).

### Panel 4 — Cumulative Shaped Reward per Satellite

Shows the running total reward each satellite has accumulated as the episode progresses. Lines diverge based on each satellite's luck (orbit geometry relative to fire locations) and decision quality.

**Reward structure:**
| Event | Reward |
|-------|--------|
| IMAGE clear sky + fire pixel | **+10.0** |
| IMAGE clear sky + no fire | **+1.0** |
| IMAGE cloud-blocked pixel | **−2.0** |
| DOWNLINK during contact window | **+2.0** |
| Battery < 0.02 (critical depletion) | **−5.0** |
| Storage > 0.98 (overflow) | **−3.0** |

The **blue shaded band** spans the best and worst satellite's cumulative reward — a narrow band means the fleet is performing homogeneously; a wide band means some satellites are far luckier or more effective. The **green `Fleet Σ =` annotation** shows the total reward for that episode.

> From `run_stats.json`, the actual fleet totals were: **Ep1: 92.0 | Ep2: 117.0 | Ep3: 133.0** — showing a learning trend across environments.

## 🛰️ Image 3 — `ep{N}_ground_tracks.png` — Orbital Ground Tracks & Coverage

> **3 files**: `ep1_ground_tracks.png`, `ep2_ground_tracks.png`, `ep3_ground_tracks.png`

This is a **2-panel spatial analysis** of where the satellites flew and what they did.

### Left Panel — Orbital Ground Tracks

A top-down map of the normalised ROI region (lat/lon [0,1] × [0,1]) showing the trajectory of each satellite as a coloured line. The satellites orbit at different periods (90–105 min), so they naturally spread across the ROI in a Walker-like pattern.

**Marker symbols show the action taken at every 4th step:**

| Marker | Action |
|--------|--------|
| `.` (dot) | IDLE |
| `*` (star) | IMAGE — the most important action, highlighted with a larger marker |
| `^` (up arrow) | STEER↑ |
| `v` (down arrow) | STEER↓ |
| `■` (square) | DOWNLINK |

> You can see which satellites sweep across fire zones (dense `*` markers) vs. which spend most time idling or steering.

**Why do the tracks curve/loop?**
Each satellite's `lon_n` is computed as `cos(phase × 0.7)` while `lat_n` is `sin(phase)`. This creates elliptical Lissajous-like orbits in the normalised ROI frame — a physically plausible approximation of ground-track swaths for sun-synchronous orbits without requiring full SGP4 propagation.

### Right Panel — Imaging Coverage Density Map

A **2D histogram heatmap** showing *where* IMAGE actions occurred across the ROI:
- The `plasma` colourmap runs from dark purple (low) to bright yellow (high) showing how densely each grid cell was imaged across the 48 steps
- **Orange stars (★)** mark positions where a satellite achieved a **fire-capture event** (reward ≥ +8, meaning it successfully imaged a fire pixel under clear sky)

> The difference between episodes is visible here: in Ep3 (Pantanal), fire captures tend to cluster around the drier margins of the wetland.

## 🧪 Key Takeaways for ML Researchers

1. **The world-state tensor is the agent's observation** — the ViT agent receives a local patch of this [8×64×64] tensor centred on its current position.

2. **Binary masks are the decision triggers** — Cloud Mask channel allows the policy to avoid wasting image captures on cloud-blocked pixels; Fire Mask tells it where to prioritise.

3. **Battery and storage are the resource constraints** — visible in the timeline plots; a well-trained MARL policy should maintain smooth curves that never breach the thresholds.

4. **Ground tracks show spatial exploration quality** — a good policy should have dense, even coverage, not just cluster around the initial fire zones.

5. **Fleet reward trajectory across episodes** (92 → 117 → 133) shows the **simulation difficulty gradient** built into the three regions — a trained agent should generalise across all three.
